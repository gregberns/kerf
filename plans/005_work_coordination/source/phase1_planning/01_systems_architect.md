# Systems Architect Brainstorm — Work Coordination

> Perspective: graph theory, data structures, information architecture, system design patterns.

---

## Idea 1: Typed Hypergraph with Area Nodes

**What it is.** Extend the work graph from a simple DAG (works connected by `depends_on` edges) to a hypergraph that includes two node types: **work nodes** and **area nodes**. Area nodes represent system components or architectural regions (e.g., "adapter layer," "auth subsystem," "database schema"). Works are connected to areas via `touches` edges. Works are connected to each other via typed edges: `blocks`, `informs`, `co-designs-with`.

A hyperedge called a **cohort** groups multiple works that touch the same area into a single relationship, distinct from pairwise edges. The cohort is not just "A and B both touch the adapter" — it is a first-class entity that can carry metadata: a shared design constraint, a reconciliation status, a designated reviewer.

**Problems addressed.** P2 (islands), P5 (coherence across modes), P4 (late-arriving requirements — new work touching an existing area automatically joins the cohort).

**How it works mechanically.**

- `spec.yaml` gains a `touches` field: a list of area slugs (e.g., `["adapter", "config"]`).
- Areas are defined in a project-level `areas.yaml` file at `~/.kerf/projects/{project-id}/areas.yaml`. Each area has a slug, a human description, and optionally a list of file globs or module paths it corresponds to in the codebase.
- `kerf new` prompts for or infers areas. `kerf show` displays area membership. A new command `kerf area` lists all areas and the works touching each.
- Cohorts are computed, not stored: any set of in-flight works sharing an area forms a cohort. `kerf area adapter` shows the cohort for the adapter area.
- When a new work is created that touches an area with in-flight works, kerf emits a warning: "3 other works also touch adapter: [list]. Consider reviewing them together."

**What's hard.**

- Area taxonomy is the crux. Too coarse (everything is "backend") and it is useless. Too fine (every file is an area) and it is noise. The taxonomy needs to be human-curated but low-friction to maintain.
- Agents may not know what areas a work touches until partway through spec-writing. The `touches` field needs to be mutable and retroactively add works to cohorts.
- Hyperedge semantics are conceptually clean but may be overkill for the query patterns actually needed. Pairwise "overlaps" edges might suffice.

## Idea 2: Materialized Work Graph with Projection Views

**What it is.** A single file (`workgraph.yaml`) at the project level that is the materialized, queryable representation of all works and their relationships. It is not a narrative (HANDOFF) or a task list (beads) but a structured graph document. kerf maintains it automatically as works are created, updated, and completed.

The graph supports multiple **projections** — different views computed from the same underlying data:

- **Dependency view:** a DAG showing what blocks what.
- **Area view:** works grouped by system component.
- **Status view:** works grouped by lifecycle stage (spec-writing, ready, implementing, done).
- **Timeline view:** works ordered by creation date, with estimated trajectory.
- **Readiness view:** works whose dependencies are satisfied and are actionable now.

**Problems addressed.** P1 (persistent map), P3 (intake/prioritization via readiness view), P2 (area view makes islands visible).

**How it works mechanically.**

- `workgraph.yaml` is generated by kerf on every state-changing command (or on demand via `kerf graph`). It reads all `spec.yaml` files in the project and computes the graph.
- The file contains: a list of work nodes (codename, status, type, jig, areas, dependencies), a list of edges (typed relationships), and computed properties (is-blocked, is-actionable, blocking-count — how many works this one blocks).
- `kerf graph` outputs a specific projection. `kerf graph --view=ready` shows actionable works. `kerf graph --view=area` groups by area. `kerf graph --view=deps` shows the dependency DAG.
- The graph file is the "session orientation" artifact — an agent reads it at session start instead of (or in addition to) HANDOFF.md.

**What's hard.**

- Staleness: the graph must be recomputed frequently. If kerf is not invoked between sessions, the graph may be stale. Could be mitigated by computing it lazily on read.
- The graph file could grow large for projects with many works. Pagination or filtering is needed.
- Projections require design: what exactly does each view contain? The readiness view needs dependency resolution. The area view needs area assignments. Each projection is its own feature.

## Idea 3: Dependency Edges with Semantic Types and Weights

**What it is.** Enrich the existing `depends_on` field from two relationship types (`must-complete-first`, `inform`) to a richer vocabulary that captures the nuance of work relationships:

| Relationship | Semantics | Constraint |
|---|---|---|
| `blocks` | Must complete before dependent can start/finalize | Hard ordering |
| `informs` | Provides context but does not block | Soft ordering |
| `co-designs` | Must be designed with mutual awareness | Synchronization |
| `supersedes` | Replaces or subsumes another work | Lifecycle |
| `amends` | Modifies an in-flight work's scope | Lifecycle |
| `conflicts` | Known incompatibility that must be resolved | Constraint |

Additionally, edges carry a **weight** (0-1) representing coupling strength. Two works that both touch the adapter but in unrelated ways get a low weight. Two works that need to share state get a high weight. Weights are advisory — they help agents and humans prioritize which overlaps to pay attention to.

**Problems addressed.** P2 (co-designs relationship makes coupling explicit), P4 (amends relationship handles late-arriving requirements), P5 (conflicts relationship surfaces contradictions).

**How it works mechanically.**

- `spec.yaml` `depends_on` entries gain the full relationship vocabulary. Backward compatible: existing `must-complete-first` maps to `blocks`, `inform` maps to `informs`.
- `kerf link <work-a> <work-b> --rel co-designs` creates a bidirectional edge.
- `kerf show <work>` displays all edges, grouped by type.
- The `co-designs` relationship triggers a special behavior: when either work advances past a design-phase status (e.g., past `decompose` or `change-spec`), kerf emits a warning if the co-designed work has not been reviewed for consistency.
- `amends` edges are created when a late requirement is added to an existing work. The amending work carries additional spec content that the amended work must incorporate. kerf tracks whether the amendment has been integrated.

**What's hard.**

- Relationship types are easy to define but hard to use correctly. Agents will need clear guidance on when to use `co-designs` vs `informs`. The taxonomy must earn its keep — unused types are dead weight.
- Bidirectional edges (co-designs, conflicts) are a departure from the current unidirectional `depends_on` model. The schema needs to handle directionality.
- Weight assignment is subjective. Automated weight inference (based on area overlap, file glob intersection) would be more useful but harder to implement.

## Idea 4: Priority Score as a Computed Property

**What it is.** Rather than storing priority as a user-assigned field (P1/P2/P3), compute a **priority score** from structural properties of the graph:

- **Fan-out:** how many works does this one block? (High fan-out = high leverage.)
- **Critical path depth:** how deep is this node in the longest dependency chain? (Deeper = less urgent. Shallower on the critical path = more urgent.)
- **Staleness:** how long since this work was last touched? (Old and incomplete = possibly stuck.)
- **Area heat:** how many in-flight works touch the same area? (Hot areas need attention sooner to prevent divergence.)
- **User boost:** an optional manual weight the user can add/remove.

The score is recomputed on every graph query. It answers "what should I work on next?" without requiring the user to manually rank everything.

**Problems addressed.** P3 (prioritization — the score IS the prioritization), P1 (the score encodes trajectory information).

**How it works mechanically.**

- `kerf next` computes scores for all actionable works (dependencies satisfied, not blocked) and emits the top N.
- The score formula is configurable but has sensible defaults. Each factor has a weight. The default weights emphasize fan-out (unblocking others) and area heat (preventing divergence).
- `kerf graph --view=priority` shows all works ordered by score with the contributing factors broken down.
- The score is ephemeral — not stored in spec.yaml. It is a view over the current graph state.

**What's hard.**

- Tuning the formula. Bad defaults make the score useless or misleading. The formula needs to be transparent (show the breakdown) so users can understand and override it.
- "Area heat" requires area assignments (Idea 1). Without areas, the score loses one of its most useful signals.
- Computed priority can feel opaque compared to explicit ranking. Some users will want "just let me say this is P1." The user boost accommodates this but creates tension between computed and manual priority.

## Idea 5: Area Spec Documents as Coherence Anchors

**What it is.** For each system area that has multiple works touching it, create an **area spec** — a short document that captures the shared design decisions and constraints for that area. Individual works touching the area must conform to the area spec. The area spec is the coherence mechanism.

This is not a full system spec (that is the project's `specs/` directory). It is a lightweight, living constraint document that captures decisions made *because* multiple works interact in this area. Example: "The adapter layer uses a decorator pattern for cross-cutting concerns. All adapter modifications must be implemented as decorators, not by modifying the base adapter."

**Problems addressed.** P2 (area specs prevent incompatible design choices), P5 (area specs provide coherence regardless of process mode), P4 (new requirements in an area inherit the area spec's constraints).

**How it works mechanically.**

- Area specs live at `~/.kerf/projects/{project-id}/areas/{area-slug}.md`.
- When a second work is created touching an area that already has an in-flight work, kerf suggests creating an area spec: "Two works now touch adapter. Consider running `kerf area spec adapter` to capture shared design constraints."
- `kerf area spec <slug>` creates a lightweight template. The agent or user fills in shared constraints.
- `kerf show <work>` includes relevant area specs in its output context. When an agent resumes a work, it sees the area constraints.
- `kerf square` checks that works referencing an area have acknowledged the area spec (a simple flag in spec.yaml: `area_specs_reviewed: [adapter]`).
- Area specs can be promoted to full system specs at any time if the design decisions prove durable.

**What's hard.**

- Area specs are another artifact to maintain. If they are not kept up to date, they become misleading — worse than not having them.
- The trigger for creating an area spec (second work touching the area) requires area assignments to exist, which requires area taxonomy (same challenge as Idea 1).
- It is unclear who updates the area spec when a work makes a design decision that affects the area. The update could happen in the work's jig passes, but that requires jig modifications.

## Idea 6: Work States as a Petri Net

**What it is.** Model the work graph as a colored Petri net rather than a simple DAG. Each work is a **place**. Each transition represents a lifecycle event (start, advance-status, finalize, amend). **Tokens** represent attention/capacity. The net's firing rules encode:

- A work can only fire (advance) if it has a token and its input places (dependencies) have tokens in their "complete" sub-place.
- Tokens are limited (representing agent capacity). If you have 3 agents, you have 3 tokens. This makes resource contention visible in the model.
- A "co-design" constraint is modeled as a synchronization transition: it requires tokens from both works simultaneously, forcing them to be designed together.

**Problems addressed.** P3 (token placement = what is being worked on; token availability = what can be started), P2 (synchronization transitions enforce co-design), P4 (amend transitions inject new requirements into an in-flight work's place).

**How it works mechanically.**

- The Petri net is a conceptual model that informs the data structures, not necessarily a literal Petri net implementation. The key insight is that **capacity is finite and shared**, so the model should make contention visible.
- `spec.yaml` gains an `assigned` field (boolean or agent-id) representing a token. `kerf assign <work>` places a token. `kerf unassign <work>` removes it.
- `kerf next` shows works that are fireable: dependencies met AND not already assigned (no token).
- Synchronization transitions surface as: "work A and work B both need design attention before either can proceed to implementation. Assign them to the same session."

**What's hard.**

- Petri nets are powerful but have a steep conceptual overhead. The model needs to be invisible to users — they should see "what's ready" and "what's blocked," not "places" and "transitions."
- Agent capacity is not really a fixed number. Agents can be spawned on demand. The token model may over-constrain.
- Synchronization transitions (co-design) require detecting when works should be synchronized, which is the same area-overlap detection problem.

## Idea 7: Event Log with Derived Views (Event Sourcing the Work Graph)

**What it is.** Instead of a materialized graph file, maintain an append-only **event log** for each project. Every work lifecycle event is recorded:

```
2026-05-01T10:00:00Z  work.created       {codename: auth-retry, type: plan, areas: [adapter]}
2026-05-01T10:05:00Z  work.status         {codename: auth-retry, from: problem-space, to: analyze}
2026-05-01T14:00:00Z  work.created       {codename: adapter-metrics, type: plan, areas: [adapter]}
2026-05-01T14:00:01Z  overlap.detected   {works: [auth-retry, adapter-metrics], area: adapter}
2026-05-02T09:00:00Z  work.linked        {from: auth-retry, to: adapter-metrics, rel: co-designs}
```

Views (map, readiness, area clustering) are derived by replaying the log. The log is the source of truth; views are computed projections.

**Problems addressed.** P1 (the log IS the persistent map — it captures everything that happened), P5 (events are recorded regardless of process mode), P4 (amendment events are first-class).

**How it works mechanically.**

- The log lives at `~/.kerf/projects/{project-id}/events.log` (or `.yaml`).
- Every kerf command that changes state appends an event. Events are timestamped, typed, and carry a payload.
- `kerf graph` replays the log and computes the current state. With caching, this is fast.
- `kerf history` shows the raw log, optionally filtered by work or area.
- Because the log is append-only, it is safe for concurrent access (multiple agents can append without conflicts, as long as appends are atomic).
- Derived views can be cached and invalidated when new events arrive.
- The log doubles as an audit trail: you can reconstruct the state of the work graph at any past point in time.

**What's hard.**

- Log replay cost grows with project size. Snapshotting (periodic materialized state) mitigates this but adds complexity.
- Events must be well-defined. A vague event schema undermines the whole approach. Each event type needs a clear payload schema.
- Concurrent appends from multiple agents need coordination. Filesystem-level atomic append (O_APPEND) works for simple cases but may not suffice if events have ordering dependencies.
- This is a significant architectural departure from kerf's current "filesystem is the database" model, where the truth is in spec.yaml files, not in a log.

## Idea 8: Conflict Detection via File Glob Intersection

**What it is.** A lightweight, automated approach to detecting overlap between works. Instead of (or in addition to) manually assigned area tags, infer overlap from the concrete files each work will modify.

During the tasks pass, works produce a task list (e.g., `07-tasks.md`). Tasks reference specific files or modules. If two works' task lists reference the same files, they have a concrete overlap.

Similarly, during the spec/plan passes, works reference specific areas of the codebase. Extracting file paths from work artifacts gives a set of "touched files" per work. The intersection of these sets is the overlap.

**Problems addressed.** P2 (overlap is detected automatically from concrete data, not manual tags), P5 (works in any process mode produce file references that can be intersected).

**How it works mechanically.**

- `spec.yaml` gains an optional `touched_files` field: a list of file globs (e.g., `["internal/adapter/*.go", "internal/adapter/retry.go"]`).
- This field is populated in two ways: (a) manually by the agent during spec-writing, or (b) automatically by parsing task artifacts for file paths.
- `kerf overlap` scans all in-flight works' `touched_files` and reports intersections: "auth-retry and adapter-metrics both touch internal/adapter/*.go".
- `kerf new` runs overlap detection automatically and warns if the new work's initial file references overlap with existing works.
- Overlap reports include a specificity score: overlapping on a single utility file is low concern; overlapping on the same core module is high concern.

**What's hard.**

- File references may not be known early enough. During problem-space and analyze passes, the concrete files are often unclear. By the tasks pass, the spec is nearly done — overlap detection is late.
- File globs are noisy. Many works touch `go.mod` or `config.yaml` — these overlaps are uninteresting. A noise filter (exclude common files, weight by path depth) is needed.
- This approach misses semantic overlap that does not manifest as file overlap. Two works can make incompatible design choices even if they touch different files (e.g., one changes an interface, the other assumes the old interface).

## Idea 9: Work Graph Invariants and Consistency Checks

**What it is.** Define a set of **graph invariants** that must hold at all times, and check them automatically. This is analogous to `kerf square` for individual works, but applied to the work graph as a whole. Call it `kerf square --graph` or `kerf audit`.

Invariants:

1. **No orphaned blockers.** If work A blocks work B, and A is archived or abandoned, B must be unblocked (the edge must be removed or the constraint must be explicitly waived).
2. **Co-design pairs must be in compatible phases.** If A and B are co-designed, they should not be more than N phases apart. (If A is in implementation and B is still in problem-space, the co-design constraint is being violated.)
3. **Area heat threshold.** If more than K works touch the same area simultaneously, warn. High concurrency in one area is a design coherence risk.
4. **Cycle detection.** The blocks-edges must form a DAG. No cycles.
5. **Completeness.** Every work in the graph should have at least one area assignment by the time it reaches the decompose pass.
6. **Stale work detection.** Works that have not been touched in N days and are not in a terminal state.

**Problems addressed.** P1 (invariant violations surface map-level problems), P2 (area heat invariant catches clustering), P5 (phase compatibility invariant catches coherence failures).

**How it works mechanically.**

- `kerf audit` reads all in-flight works, builds the graph, and checks all invariants. It emits a report.
- Each invariant has a severity (error, warning, info). Errors are things like cycles in the blocks-graph. Warnings are things like area heat. Info is stale work detection.
- `kerf audit` can be run by an agent at session start as part of orientation. The audit report replaces or supplements the HANDOFF narrative for graph-level awareness.
- Invariants are defined in a config file or hardcoded with sensible defaults. Users can adjust thresholds (area heat K, staleness N days, phase distance for co-design).

**What's hard.**

- Invariant definitions are opinionated. Different projects have different tolerances. The system needs good defaults and easy overrides.
- Some invariants (like co-design phase compatibility) require the co-design relationship to exist, which depends on agents or users creating those edges.
- Running `kerf audit` requires reading all works. For large portfolios, this could be slow. Caching or incremental computation helps.

## Idea 10: Session Orientation Document (Computed, Not Written)

**What it is.** Replace the hand-written HANDOFF.md with a **computed orientation document** that kerf generates at session start. This document combines:

- The work graph state (from Idea 2 or 7)
- The current work's full context (status, dependencies, area memberships)
- Recent events (what changed since the last session)
- Actionable warnings (from Idea 9's invariant checks)
- Next steps derived from the jig's current pass and the work's position in the graph

The key insight: HANDOFF.md fails because it is written by the ending session (which has a narrow view of what the next session will need) and read by the starting session (which needs broad orientation). A computed document can include graph-level context that no single session has.

**Problems addressed.** P1 (the orientation document IS the persistent map, customized per session), P3 (it includes "what's next" based on priority scores), P5 (it includes coherence warnings from area overlap detection).

**How it works mechanically.**

- `kerf orient` (or integrated into `kerf resume`) generates the document. It reads the work graph, the current work's state, and recent events.
- The output is structured markdown with sections: Graph Overview, Current Work, Recent Changes, Warnings, Suggested Next Steps.
- The document is ephemeral — regenerated each time, not stored. (Or stored as a snapshot for debugging.)
- It replaces the "read HANDOFF.md" step in agent session startup. Instead: `kerf orient <codename>` and the agent has full context.
- The "recent changes" section uses diffs: what works were created, what statuses changed, what new overlaps were detected since the last session for this work.

**What's hard.**

- The document must be concise enough for an agent's context window. A project with 20 works and complex relationships could produce a very long orientation. Summarization or filtering is needed.
- "Recent changes" requires knowing when the last session was, which requires session tracking (already in spec.yaml).
- This is a consumer of other ideas (graph, areas, priorities, invariants). It is only as good as the underlying data.

## Idea 11: Entanglement Protocol for Late-Arriving Requirements

**What it is.** A defined protocol — not just a data structure — for handling Problem 4: a new requirement arrives that is architecturally entangled with an in-flight work. The protocol has three paths:

**Path A: Amend.** The new requirement is small enough to fold into the in-flight work. Create an amendment record in the in-flight work's spec.yaml. The amendment includes: what changed, which tasks are affected, whether any completed tasks need revision. The jig's implementation pass instructions include "check for amendments before starting each task batch."

**Path B: Spawn dependent.** The new requirement is large enough to be its own work but architecturally coupled to the in-flight work. Create a new work with a `co-designs` edge to the in-flight work. The new work's spec includes an explicit "inherits from" section referencing the in-flight work's design decisions. The in-flight work gets a note: "design decisions here are load-bearing for [new-work]."

**Path C: Pause and re-plan.** The overlap is so deep that continuing the in-flight work independently would create more rework than pausing. The in-flight work is shelved. A new combined work is created that supersedes both. Completed tasks from the original work are marked as "potentially reusable" in the new work's task list.

**Problems addressed.** P4 (directly — this IS the late-requirement protocol), P2 (the protocol forces explicit handling of entanglement rather than ignoring it).

**How it works mechanically.**

- `kerf amend <codename>` adds an amendment record to spec.yaml. The record includes: description, affected areas, affected tasks (optional), date.
- `kerf link <new-work> <in-flight-work> --rel co-designs` (Path B). The co-designs edge triggers kerf to include the in-flight work's design decisions in the new work's context.
- `kerf supersede <old-work> --with <new-work>` (Path C). The old work is shelved with a note pointing to the new work. The new work's spec.yaml records the superseded work's codename.
- The choice between paths is not automated — it requires human or orchestrator judgment. But kerf can suggest: "The new requirement touches 4 of 7 areas in the in-flight work. Consider Path C (pause and re-plan)."

**What's hard.**

- Path C (pause and re-plan) means throwing away in-progress work. This is psychologically and practically expensive. The protocol needs to make the cost/benefit clear.
- Amendments (Path A) can accumulate, turning a clean spec into a patchwork. There should be a limit or a "consolidation" step.
- The choice between paths requires judgment that agents may not have. Clear heuristics (overlap percentage, completion percentage of in-flight work) can help but are not definitive.

## Cross-Cutting Observations

**The area taxonomy is the linchpin.** Ideas 1, 4, 5, 8, and 9 all depend on knowing what system areas each work touches. This is the single most valuable piece of metadata to add. Without it, overlap detection is manual. With it, most of the coordination problems become queryable.

**Computed views beat stored state.** The filesystem-is-the-database principle means the graph should be computed from spec.yaml files, not stored separately. Materialized views (workgraph.yaml) are caches, not sources of truth. This avoids consistency problems.

**Edges need more types.** The current two-type relationship model (`must-complete-first`, `inform`) is insufficient. At minimum, add `co-designs` (synchronization) and `supersedes` (lifecycle). These two additions address Problems 2 and 4 directly.

**The orientation problem is a read-path problem.** The graph, areas, priorities, and invariants are all write-side structures. The orientation document (Idea 10) is the read-side integration point — it assembles all of these into what the agent actually needs at session start. Solving the write side without solving the read side leaves the agent in the same position: unable to orient.

**Minimal viable coordination.** If forced to pick three changes with maximum leverage:
1. Add area tags to works (foundation for overlap detection)
2. Add `co-designs` relationship type (makes entanglement explicit)
3. Add `kerf orient` command (makes the graph legible to agents at session start)

Everything else builds on these three.
